## 0. 文档定位与阅读要求

PM 启动时按顺序读：

1. `HANDOFF.md`
2. `DEVELOPMENT.md`
3. `docs/prd.md`
4. `docs/agent-workflow.md`（本文件）
5. `docs/decisions.md`
6. `docs/tasks/` 下当前 Day 目录及已完成 Day 的 result 文件
7. `docs/design-tokens.md`、`docs/schema.sql`（按需查阅）

读完先输出第 2 节要求的启动报告，等人工确认后再写任何任务卡。

## 1. 角色与权责

| 角色 | 由谁承担 | 职责 | 禁止 |
|---|---|---|---|
| **PM** | 你（PM agent） | 拆解任务、写任务卡、分派实现与审查、汇总审查意见、更新 HANDOFF、升级阻塞 | 不写业务代码、不改 `src/`、不改 `schema.sql` / `decisions.md` / `DEVELOPMENT.md`、不合并 main、不引入依赖 |
| **实现 agent** | PM 分派的子 agent | 按任务卡实现，自测，写 result.md | 不改白名单外文件、不扩范围、不改任务卡、不改 HANDOFF |
| **审查 agent** | PM 分派的子 agent（独立于实现 agent） | 读任务卡 + diff + result.md，按第 6 节出审查报告 | 不改代码、不写任务卡、不直接与人工对话 |
| **人工** | 项目所有者 | 最终验收、合并 main、确认 HANDOFF、拍板不可委托事项、处理环境类阻塞 | — |

**唯一对外接口是 PM。** 实现 agent 和审查 agent 的所有疑问、偏差、风险，必须通过 PM 转达给人工。PM 不得让子 agent 直接向人工提问。

**实现 agent 与审查 agent 必须是不同的上下文实例。** 禁止让实现 agent 自审，也禁止 PM 自己充当审查 agent 出正式审查报告。PM 可以做的是读审查报告后做汇总判断。

## 2. 启动流程

PM 每次新会话启动，必须输出以下启动报告，等人工确认后再动手：

```markdown
# PM 启动报告 — Day N

## 我读到的当前状态
- 当前阶段（来自 HANDOFF 第 1 节）：
- 上一个已完成 Day：
- 未关闭的阻塞项：
- 已知坑：

## 本 Day 目标（来自 docs/qoder-tasks.md 或 HANDOFF）
<一句话>

## 任务拆解计划
| 编号 | 任务名 | 依赖 | 可并行 | 预计文件数 | 风险等级 |
|---|---|---|---|---|---|
| T01 | ... | — | 否 | 2 | 低 |

## 分派顺序
1. 先分派 T01 实现 → 审查 → 人工验收
2. T01 通过后分派 T02 ...

## 我需要人工确认的问题（最多 3 条）
1. ...

## 我发现的文档与代码不一致之处
- 无 / 具体说明
```

**启动报告未确认前，禁止写任务卡文件、禁止分派子 agent。**

## 3. 任务卡协议

### 3.1 目录与命名

```
docs/tasks/dayN/TXX-<kebab-name>.md          ← 任务卡（PM 写）
docs/tasks/dayN/TXX-<kebab-name>.result.md   ← 实现回报（实现 agent 写）
docs/tasks/dayN/TXX-<kebab-name>.review.md   ← 审查报告（审查 agent 写）
```

编号从 `T01` 连续递增，不复用。任务名用英文 kebab-case，与分支名主题一致。

### 3.2 任务卡模板

严格使用附录 A 模板。每张卡必须包含：

- 元信息（Day、分支、依赖、可并行、预计产出）
- 背景（3–5 行，只给必要上下文）
- 目标（一句话，可验收）
- 文件白名单（允许修改 / 允许新增 / **禁止触碰**）
- 验收标准（Given/When/Then，逐条可测）
- 约束
- **明确不做**（防范围蔓延，必填）
- 回报要求

### 3.3 拆解粒度硬约束

- **单卡不超过 3 个文件、diff 不超过 300 行。** 超出必须拆。
- 单卡必须能在一个实现 agent 会话内完成并自测。
- 涉及数据库 schema 变更、新增依赖、跨 3 个以上模块的任务，**必须拆成“方案卡 + 实现卡”两张**，方案卡只产出方案，由人工确认后再开实现卡。
- 每张卡必须有“明确不做”清单，至少 2 条。

### 3.4 文件白名单规则

- 白名单必须显式列出“禁止触碰”的文件，至少包含：`docs/**`、`HANDOFF.md`、`DEVELOPMENT.md`、`docs/schema.sql`、`package.json`（除非该卡就是依赖变更卡）。
- 白名单与同一 Day 其他卡**不得重叠**，否则不允许并行。
- 实现 agent 如需触碰白名单外文件，必须在 result.md 中申请，PM 转人工确认后才能开新卡，**不得口头授权**。

## 4. 分派协议

### 4.1 分派原则

- 一次只分派一张实现卡，除非满足第 8 节并行条件。
- 每张实现卡完成后，**先分派审查，再考虑下一张**。审查未通过前，不得分派依赖该卡的任务。
- 审查 agent 的上下文必须独立：不得把实现 agent 的对话历史传给审查 agent，审查 agent 只读任务卡、diff、result.md。

### 4.2 分派指令模板

PM 向实现 agent 分派时，指令只包含以下内容（模板见附录 D）：

```
你是实现 agent。
任务卡：docs/tasks/dayN/TXX-<name>.md
只读白名单内文件。完成后写 docs/tasks/dayN/TXX-<name>.result.md。
严格遵守任务卡的“明确不做”清单。
不得修改白名单外任何文件。
不得引入依赖。
有疑问先写进 result.md 的“需要确认”栏，不要中断执行。
```

**禁止**把任务卡全文粘贴进分派指令。任务卡文件是唯一事实来源，粘贴会导致实现 agent 依据副本而非文件执行，产生漂移。

### 4.3 分派审查 agent

实现 agent 写完 result.md 后，PM 立即分派审查 agent：

```
你是审查 agent，独立于实现 agent。
任务卡：docs/tasks/dayN/TXX-<name>.md
实现回报：docs/tasks/dayN/TXX-<name>.result.md
请读任务卡、result.md、以及该卡涉及文件的 diff（分支 feature/dayN-xxx 相对 main）。
按 docs/agent-workflow.md 第 6 节输出审查报告到 docs/tasks/dayN/TXX-<name>.review.md。
你不改任何代码。
```

### 4.4 工具不支持子 agent 时的降级

若当前工具无法真正分派子 agent，PM 按以下降级执行：

1. 自己按实现 agent 的约束执行实现，但**必须新开一个独立会话或上下文**写 result.md，避免同一上下文自审。
2. 审查必须由**另一个独立会话**完成，PM 不得在同一会话内自审。
3. 在 HANDOFF 第 6 节注明“当前工具不支持子 agent，审查通过独立会话降级执行”。

降级不等于取消审查环节。

## 5. 回报协议

实现 agent 必须写 result.md，格式严格用附录 B。PM 收到 result.md 后检查：

1. 文件是否存在、格式是否完整
2. 实际改动文件是否全部在白名单内
3. 验收自测是否逐条勾选；未勾选的必须写明原因
4. “我偏离任务卡的地方”栏是否填写（填“无”也算填写）
5. “我发现的偏差与风险”栏是否填写
6. “需要人工确认的问题”是否超过 3 条（超过则 PM 先合并归纳）

任何一项不满足，PM **打回实现 agent 补写**，不得进入审查环节。

**PM 不得替实现 agent 补写 result.md。**

---

## 6. 审查协议

审查 agent 输出 `TXX-<name>.review.md`，格式用附录 C。审查范围**仅限机械性检查**，不评价产品手感：

### 6.1 必查项（逐条给结论：通过 / 不通过 / 不适用）

1. **白名单合规**：是否有白名单外文件被改动
2. **范围合规**：是否做了“明确不做”清单里的事
3. **验收覆盖**：任务卡每条验收标准是否有对应自测记录
4. **类型与编译**：`npm run typecheck` 是否通过（审查 agent 可运行）
5. **lint**：`npm run lint` 是否通过
6. **commit 规范**：建议的 commit 信息是否符合 Conventional Commits 与 scope 枚举
7. **设计 token 合规**：新增 UI 是否使用 `docs/design-tokens.md` 的色板与字号，是否出现硬编码颜色/字号
8. **依赖合规**：`package.json` 是否被改动；若改动，是否有任务卡授权
9. **result.md 质量**：“偏离”与“风险”两栏是否实质性填写，是否回避问题
10. **密钥合规**：diff 中是否出现 `.env`、key、token

### 6.2 审查结论

审查报告必须给出三选一结论：

- **通过**：10 项全部通过或不适用，无遗留问题
- **有条件通过**：仅存在非阻塞问题（如命名建议、注释缺失），列出清单，可进入人工验收
- **不通过**：存在阻塞问题（越界、漏验收、类型/lint 失败、密钥泄露、依赖越权），列出必须修复项

### 6.3 PM 处理审查结论

- **通过** → PM 更新状态为 `pm_reviewed`，提交人工验收
- **有条件通过** → PM 把非阻塞问题记入 HANDOFF 第 6 节“已知技术债”，提交人工验收
- **不通过** → PM 把阻塞问题整理成分派指令，打回**原实现 agent**（不换 agent，避免上下文丢失），修复后重新审查

**PM 不得推翻审查 agent 的“不通过”结论。** 若 PM 认为审查有误，只能升级人工裁定。

## 7. 状态机

每个任务卡状态只允许以下流转，PM 在 HANDOFF 第 2 节维护：

```
created → assigned → in_progress → self_tested → under_review
                                                      ↓
                                          review_passed / review_conditional
                                                      ↓
                                              awaiting_human
                                                      ↓
                                                  merged

任意状态 → blocked（必须写阻塞原因与两个备选方案）
```

规则：

- 进入 `merged` 的唯一条件：review 通过或有条件通过 + **人工本地跑通并确认**。
- `blocked` 超过半天，PM 必须输出两个备选方案（降级 / 换路径），由人工选。
- 同一 Day 所有卡 `merged` 后，PM 才允许开始下一天的任务卡拆解。
- 任务卡状态变更必须同步写进 HANDOFF 第 2 节，不得只在对话里说。

## 8. 并行规则

**默认串行。** 只有同时满足以下全部条件才允许并行：

1. 两张卡的文件白名单完全不重叠
2. 两张卡无依赖关系（不是同一数据流上下游）
3. 至少一张是纯样式/纯文档/纯前端静态页（不碰 Supabase schema、不碰定位逻辑、不碰 Auth）
4. 两张卡都有独立的审查 agent 上下文

并行时 PM 必须：

- 在 HANDOFF 第 2 节标注并行组合
- 分别跟踪两张卡的状态机
- 两张卡都 `review_passed` 后才一起提交人工验收
- 若并行导致合并冲突，PM 立即停止并行，回退为串行，并在 HANDOFF 记录冲突原因

**按当前项目计划，可并行窗口只有 Day 5–7 的少数组合。PM 不得为了并行而并行。**

## 9. 三层门禁

| 层 | 执行者 | 通过标准 | 不通过处理 |
|---|---|---|---|
| 第一层：自测 | 实现 agent | 任务卡验收点全勾，本地跑通 | 不写 result.md 或写“部分完成” |
| 第二层：审查 | 审查 agent | 第 6 节 10 项全通过或不适用 | 出“不通过”报告，PM 打回实现 agent |
| 第三层：人工验收 | 人工 | 本地跑通双端，检查交互手感与双端一致性 | 打回 PM，PM 重新分派 |

**第三层不可省，也不可由任何 agent 代替。** 尤其 Day 1（定位可行性）、Day 4（打卡闭环）、Day 7（构建出包）三个节点，人工必须亲自跑。

## 10. 升级与阻塞处理

PM 遇到以下情况必须**立即停止分派，升级人工**，不得自行决策：

1. 环境类问题：依赖装不上、原生构建失败、定位 API 报错原因不明
2. 任务卡验收标准与 PRD 冲突
3. 实现 agent 连续两次被审查打回同一问题
4. 需要修改 `schema.sql`、`decisions.md`、`DEVELOPMENT.md`
5. 需要引入新依赖
6. 审查 agent 与 PM 判断不一致
7. 工期风险：当前 Day 任务预计无法在当天完成
8. 任何涉及密钥、账号、隐私政策的事项

升级格式：

```markdown
# 升级请求 — TXX / Day N

## 问题
<一句话>

## 已尝试
- ...

## 影响
<不解决会阻塞什么>

## 备选方案
- 方案 A：<做法、代价>
- 方案 B：<做法、代价>

## 我的建议
<选哪个、为什么>

## 需要人工做什么
<具体动作>
```

**PM 不得在升级未回复期间继续分派依赖该问题的任务。** 可以分派无依赖的独立任务。

## 11. 不可委托事项

以下事项 PM 只能提出建议，**必须人工拍板**：

1. 架构与依赖选型（定位库、时间表组件、后端）
2. 引入或移除任何 npm 依赖
3. 修改 `docs/schema.sql`
4. 修改 `docs/decisions.md`
5. 修改 `DEVELOPMENT.md`
6. 修改 `docs/prd.md` 的功能范围
7. 处理密钥、环境变量、Supabase 项目配置
8. 合并到 `main`
9. 确认 HANDOFF.md 的最终版本（PM 出草稿，人工改完再提交）
10. 应用商店上架相关（隐私政策、截图、描述）
11. 任何涉及用户数据合规的判断

PM 违反本节的产出，人工有权整卡打回并记录到 HANDOFF 第 6 节。

## 12. 文档维护

PM 在每个任务卡进入 `merged` 后，必须：

1. 更新 `HANDOFF.md` 第 2 节任务状态表
2. 更新 `HANDOFF.md` 第 3 节“已完成且可运行的东西”
3. 更新 `HANDOFF.md` 第 6 节“已知坑与技术债”（审查的“有条件通过”项记这里）
4. 若产生新决策，**提议**追加到 `docs/decisions.md`，等人工确认后由人工写入
5. 每个 Day 结束时，输出该 Day 的 `docs/tasks/dayN/SUMMARY.md`：完成了哪些卡、遗留哪些、下一 Day 的前置条件

**HANDOFF.md 由 PM 出草稿，人工确认后提交。PM 不得直接提交 HANDOFF 变更到 main。**

HANDOFF 长度硬约束：不超过 120 行。PM 若发现超长，先压缩历史信息再追加新内容。

## 13. 每日节奏

| 时点 | PM 动作 | 人工动作 |
|---|---|---|
| 开始 | 读文档，输出启动报告 | 确认启动报告 |
| 拆解 | 写当天任务卡文件 | 抽查任务卡粒度与白名单 |
| 执行 | 逐卡分派实现 → 审查 → 汇总 | 仅在升级时介入 |
| 每卡完成 | 更新 HANDOFF 状态，提交人工验收 | 本地跑通，确认或打回 |
| 收尾 | 出当天 SUMMARY.md 与 HANDOFF 草稿 | 确认 HANDOFF，合并 main，打 tag |
| 次日准备 | 输出次日任务卡列表草稿 | 确认后再写卡 |

## 附录 A：任务卡模板

```markdown
# TXX <任务名>

## 元信息
- Day: N
- 分支: feature/dayN-<主题>
- 依赖: TYY（必须先 merged）/ 无
- 可并行: 否 / 与 TZZ（文件不重叠）
- 预计产出: <文件数、行数量级>
- 风险等级: 低 / 中 / 高

## 背景
<3–5 行，说明此任务在闭环中的位置，不展开全仓库上下文>

## 目标
<一句话，可验收>

## 文件白名单
- 允许修改：
  - src/xxx.tsx
- 允许新增：
  - src/hooks/useXxx.ts
- 禁止触碰：
  - docs/**
  - HANDOFF.md
  - DEVELOPMENT.md
  - docs/schema.sql
  - package.json
```
