# 决策记录（ADR 简化版）

> 只记录会影响后续开发方向的决策。新增决策追加到末尾，不修改历史条目；如需推翻，新增一条并注明 supersedes。

## ADR-001 后端选用 Supabase
- 日期：2026-10-17
- 背景：Firebase 在国内访问受限，可能直接不可用
- 决策：用 Supabase，选日本/韩国/新加坡节点
- 后果：国内有数百毫秒延迟，MVP 可接受；未来可自部署

## ADR-002 第一版登录用邮箱
- 日期：2026-10-17
- 背景：短信验证码有持续成本与报备流程，一周工期不允许
- 决策：邮箱 + 密码 / 邮箱验证码
- 后果：手机号登录延后；用户注册门槛略高

## ADR-003 打卡附着于计划，不独立建表
- 日期：2026-10-17
- 背景：产品核心是时间表，打卡是计划的附属行为
- 决策：checkins 必须关联 plan_id，不支持独立打卡
- 后果：所有打卡入口都从计划进入；统计按计划聚合

## ADR-004 不做防作弊与轨迹记录
- 日期：2026-10-17
- 背景：一周工期 + 隐私最小化
- 决策：仅客户端 Haversine 判断围栏，不存轨迹，不做模拟定位检测
- 后果：存在作弊可能，接受；后续如需要再加

## ADR-005 时间表组件选型
- 日期：2026-10-17
- 背景：一周工期，需要可控的周网格
- 决策：优先 `@symbiot.dev/react-native-timegrid`，Day 1 验证；失败降级 `react-native-calendar-timetable`，再不行自绘
- 后果：Day 1 必须完成验证，否则影响 Day 2

## ADR-006 自主授权与跨 Agent 接力
- 日期：2026-10-21
- 背景：用户纠正旧文档把环境、账号、依赖、部署与 Git 操作交人工的要求。
- 决策：主控自主规划、配置、排错、维护规范 / Schema、提交推送及检查后合并部署；代码在新分支通过子任务实现并独立审查。
- 替代：旧规范中的启动确认、依赖确认、逐卡人工验收、人工合并与人工提交 HANDOFF。
- 后果：仅缺秘密 / 交互验证、产品冲突、重大架构或范围变化等升级；授权不能当作已登录或已部署。

## ADR-007 第一周范围收敛
- 日期：2026-10-21
- 背景：新需求聚焦极简学习闭环，旧文档额外承诺通知、重复和第二周社交。
- 决策：通知、拖拽、复制 / 重复 / 顺延及社交只记候选 backlog，未自动排期。
- 后果：先完成核心闭环，不改变既定技术栈，不提前承诺第二周功能。

## ADR-008 地点可选与秘密边界
- 日期：2026-10-21
- 背景：新需求地点可选，旧 PRD 却只允许绑定后打卡；旧配置将 Web 服务 Key 暴露给客户端。
- 决策：无围栏只检验时间；有围栏请求一次前台位置。高德 Web 服务 Key 放服务端鉴权代理，原生 SDK Key 独立配置。
- 后果：不采集后台位置或轨迹，不使用 EXPO_PUBLIC_AMAP_WEB_KEY。

## ADR-009 纠正旧标题歧义
- 日期：2026-10-21
- 背景：ADR-003 标题“不独立建表”与其正文和 Schema 矛盾。
- 决策：保留独立 checkins 表，但必须关联本人计划，不支持脱离计划打卡；旧标题不代表取消表。
- 后果：正式 Schema 需约束计划所有权和每计划唯一打卡，不能仅靠客户端。

## ADR-010 数据库写入与统计合同
- 日期：2026-10-21
- 背景：旧 Schema 允许客户端任意写时长，统计 view 与软删除口径不完整。
- 决策：基础层只开放本人计划操作，打卡由后续受保护 RPC 写入；每计划唯一且同用户关联，历史保留原科目 / 学习日期快照，统计 view 使用 security_invoker。
- 决策：完成率分子与分母来自同一非删除计划集合，包含区间内未来计划；已有打卡不因软删除计划丢失。
- 后果：基础迁移不能代表完整打卡后端，最终业务 RPC 待时间与总结规则明确后实现。

## ADR-011 可见计划时间范围
- 日期：2026-10-21
- 背景：第一周网格08:00–23:00，原表单范围不受限，会保存不可见计划。
- 决策：第一周表单 / 数据库均限制计划在其记录时区的08:00–23:00、至少15分钟且同日。
- 后果：全天网格另记候选，不能只让界面隐藏超出范围的计划。

## ADR-012 时间表发布缺陷与版本固定
- 日期：2026-10-21
- 背景：T01 的 Web 静态渲染发现 timegrid0.2.4 崩溃；实现和只读排查两个上下文确认 Provider / hook 分别使用不同 Context，0.2.3也存在同样缺陷。Android JS打包不会执行这一渲染路径，不能据此判定可用。
- 决策：优先验证并精确固定同库0.2.2，其 Provider / hook 使用同一 Context；不直接修改 node_modules，不引入长期 fork，不因这个问题替换整体技术栈。
- 后果：是否已通过以 T01 最终运行 / 浏览器证据为准；CI 加入 Web 静态渲染导出。未经复验不能盲目升级到0.2.3/0.2.4；原生仍需设备验证。

## ADR-013 登录方案与历史假设澄清
- 日期：2026-10-21
- 背景：ADR-001 曾预设云节点和国内延迟，ADR-002 曾并列邮箱密码与邮箱验证码；初始化阶段尚无云端实测。
- 决策：第一周采用邮箱 + 密码，邮箱确认按真实项目设置验证，替代 ADR-002 的邮箱验证码候选。Supabase 区域须以实际建项目结果记录，网络可达性与延迟须实测，ADR-001 的数字不作为验收证据。
- 后果：账号、项目、注册发信和连接性能仍待真实服务验证；不得从历史决策推断已部署或可用。
